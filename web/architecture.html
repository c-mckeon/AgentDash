Latest milestone · 12 October 2026

Step 4 is done: an AI agent now does real work inside a sandbox. Given a task in plain words and a repository, the system starts a sandbox, puts the agent in it, and the agent asks the model what to do, reads and writes files, runs commands, and hands back a patch, with every step recorded. Three first tasks were run: one was done correctly, one got stuck and was stopped automatically, and one was reported as done when it was wrong. That last result is the clearest argument so far for the supervisor planned in step 7. Details are on the Research tab.

Step 1 Model service and gateway Done

Corrected after research (12 October 2026)

What follows is step 1 as first built. The research done afterwards changed three things:

  • The model is limited to 4 processor threads. Left alone it used about 19 cores, which Modal charges for; the limit gave the same writing speed at about half the cost.
  • The ledger charges each call for the idle and start/stop time around it, not only the call.
  • The budget hard stop uses the larger of our ledger and Modal's own meter. The ledger alone had been recording about an eighth of the real bill.

The gateway also gained an option to force the model's reply to be JSON, which the harness will need.

Architecture at this step

Three things are built and running on Modal: a machine image containing Ollama and the Qwen model, a model service that starts a machine from that image whenever it is called, and the gateway, which is the only part with a public web address. A prompt sent to the gateway comes back with an answer, a cost, and the remaining budget.

What was checked on the live system

  • A prompt sent through the gateway returned an answer, with token counts, seconds and cost attached.
  • First call after idle: about 8 to 10 seconds, half of it waking the machine. Calls while it is awake: well under a second for a short reply.
  • Requests with no key or a wrong key were refused.
  • With the budget limit temporarily set below what had been spent, the gateway refused the request without waking the model. The limit was then restored.
  • The ledger survived redeploys: five calls recorded, about a quarter of a cent in total.

The budget limit is set to $0.50 for now, not €10, because the Modal account has only $1 of free credit. The gateway's own small machine is not yet counted in the ledger, so Modal's bill will be slightly higher than the ledger says.

What the gateway is

A small program of ours that sits between anything that wants to use a model and the model itself. Every model request goes through it; nothing talks to the model directly.

agent in a sandbox ─┐
triage (router)     ├─►  GATEWAY  ─►  model endpoint (Ollama + Qwen on Modal)
supervisor         ─┘

Think of a reception desk in front of an expensive specialist. Reception checks you are allowed in, logs the visit, sends you to the right room, and turns you away once the month's budget is gone.

JobWhat it doesWhy it matters
Counting Records, for every request, the tokens in and out, how long the model took, and which run and role (worker, triage, supervisor) asked. The dashboard's cost and compute view is built from these records.
Budget hard stop Checks the month's spend before forwarding a request and refuses once the €10 allowance is used up. Modal's Starter plan has no spending limit of its own, so this is the only guard. It is why the gateway is built first.
Routing by registry Holds the list of which models exist and where they live. A caller asks for "the small tier"; the gateway knows which model and address that means. Adding a larger model later is a new line in the list. Callers do not change.
Keeping secrets out of sandboxes Checks the short-lived pass each run is given. Any real API key added later lives here. A sandbox runs code an AI wrote, so it should hold nothing worth stealing.

What it is not: it is not the model, not Ollama and not Modal, and it generates nothing. It is also not the harness. The harness decides what to ask the model; the gateway only carries the question and logs it. The smoke test had no gateway: the script talked straight to Ollama on the same machine, which left no record and no spending limit.

Biggest questions at this version

What is a harness, and do we have one yet?
A harness is the program that runs a model in a loop: send the task, read the model's reply, carry out the tool it asked for, send the result back, repeat. We do not have one yet; it is step 4. The smoke test imitated a single turn of that loop by hand and stopped.
Where does Ollama fit?
Ollama is the program that loads a model file and answers requests with it. It is not a harness and not a computer. Here it runs inside the Modal machine and serves the Qwen model.
What does Modal do that Ollama and Hugging Face do not?
Modal is the computer. Hugging Face and Ollama's library are where model files are downloaded from; Ollama runs a model once it has a machine. Since nothing runs on the PC, Modal rents us that machine by the second, and later it will also provide the sandboxes.
What did the smoke test prove?
That a 1.5B model on 4 CPU cores writes about 26 tokens per second and loads in 3.5 seconds, which is fast enough to continue. It also showed the model picks the right tool but writes the call in the wrong shape, so our harness will need a forgiving parser.
Why do we need a model service as well as the gateway?
The smoke test started a machine, asked two questions and shut it down, and only that one script could talk to the model. The gateway needs something it can forward to at any moment. The model service is the same image wrapped so that it wakes when called and sleeps when idle. They are separate machines on purpose: the gateway is tiny and cheap, so checking a key or refusing an over-budget request never wakes the expensive 4-core machine.
Could the gateway move into the control dashboard later?
Yes. Its rules (registry, pricing, budget, request checks) are in one file with no ties to Modal, so they can be lifted into another server. Only the thin web wrapper would be rewritten.
Still open
Whether to add a payment card to Modal, since only $1 of credit is available without one. The gateway is written in Python because it runs on Modal, which is an exception to the plan of TypeScript everywhere.

Step 2 Sandbox Done

Architecture at this step

A sandbox is a disposable computer: created for one run, used, then destroyed. This step adds the code that asks Modal for one and the definition of what is installed on it. Nothing drives a sandbox automatically yet; a test script on the PC does it by hand. The orchestrator takes over in step 3 and the agent moves in at step 4.

Built in earlier steps Added in this step Later steps

What this step adds

PieceWhat it is for
Sandbox imageThe list of what every sandbox starts with: Node (the agent will be written in TypeScript and run there), git (to fetch the repository and produce the patch) and ripgrep (fast file search for the agent).
Sandbox providerFour operations behind a plain interface: create a sandbox, run a command in it, destroy it, and report how long it lived and roughly what it cost. The rest of the system will only ever see that interface, so a different vendor could be swapped in.
Safety limitsEvery sandbox has a maximum lifetime (10 minutes by default) enforced by Modal, so a forgotten one cannot keep billing. Every command has a time limit. Processor use is capped at what is reserved, so a sandbox-second has a predictable price.

What was checked on the live system

  • A sandbox was created in 1.2 to 2.2 seconds once its image had been built.
  • Inside it: git, ripgrep and Node all present; a public repository cloned in half a second; a file edited; git diff returned the change as a patch.
  • From inside the sandbox, the gateway answered. That is the path the agent will use to reach the model.
  • A failing command reported its exit code and error text. A command that ran past its time limit was stopped and reported as timed out, and the sandbox was still usable afterwards.
  • After destroy, Modal reported the sandbox as stopped and listed no running containers. Each test lived 7 to 10 seconds and cost a few hundredths of a cent.

One surprise: when a command hits its time limit, Modal's library sometimes raises an error and sometimes reports the command as killed. The provider handles both and reports one consistent result.

Questions this version raises

Why does each run need its own computer?
The agent runs shell commands and edits files that an AI model chose. A sandbox means the worst it can do is damage a machine that is about to be deleted anyway, and one run cannot see or disturb another.
Why is this part TypeScript when the gateway is Python?
The plan is TypeScript everywhere. The gateway and model service are Python only because they run inside Modal, which is built around Python. The sandbox provider runs on our side (later inside the orchestrator), and Modal offers a TypeScript library for creating sandboxes, so the plan holds here.
Does the sandbox hold any secrets?
No. It clones a public repository, so it needs no git credentials. When the agent arrives it will carry only a short-lived pass for the gateway.
Is sandbox cost inside the budget hard stop?
Yes, since the research changes: the hard stop reads Modal's meter for the whole workspace, which includes sandboxes. The gateway's own ledger does not list sandbox time yet; the orchestrator will record it in step 3.
Still open
The live check is run from the PC. Once the orchestrator exists it should run in the cloud like everything else.

Step 3 Skeleton: API, database, orchestrator Done

Architecture at this step

Until now the pieces existed separately and were poked by hand. This step adds the part that ties them together: a server that accepts "start a run", an orchestrator that carries the run through its stages, and a database that remembers everything that happened. There is still no agent, so a run clones the repository and hands back an empty patch.

Built in earlier steps Added in this step Later steps

What this step adds

PieceWhat it is for
APIThe front door. Anyone may read runs and their events; starting or killing a run needs the owner's token. It only accepts public GitHub addresses, so a sandbox never needs credentials.
OrchestratorCarries one run through its stages in order and refuses illegal moves (a finished run can never restart; stages cannot be skipped). It checks for a kill request between stages and always destroys the sandbox, whatever happens.
DatabaseRemembers runs, the ordered event log, which model was chosen and why, the patch, and what the sandbox cost. The event log is what the dashboard's live feed and replay will be built from.
Per-run passA short-lived pass, valid for one run, that a sandbox uses to reach the gateway. The gateway checks it by arithmetic alone, with no lookup, and records the call against that run as "worker" whatever the caller claims.
ConfigOne place that reads settings and secrets from the environment and complains clearly if any are missing.

What was checked on the live system

  • A normal run went queued → triaging → running → reviewing → done in about 7 seconds, with 13 events logged, and cost $0.0003 of sandbox time.
  • A run pointed at a repository that does not exist ended as "failed" with a clear reason, and its sandbox was still destroyed.
  • A run killed straight after starting ended as "killed" and its sandbox was destroyed 0.7 seconds after it was created.
  • From inside the sandbox, the run's pass was accepted by the gateway. Outside it, an expired pass, a pass altered to name another run, and a pass signed with the wrong key were all refused.
  • None of this woke the model, so it cost no model time.

Questions this version raises

What is an orchestrator, as opposed to the agent?
The orchestrator is the stage manager: it sets up the sandbox, starts things in the right order, watches for a kill request, and cleans up. It makes no decisions about code. The agent is the performer: it decides what to read, edit and run. This step built the stage manager; the performer arrives next.
Why SQLite when the plan said hosted Postgres?
Postgres needs an account with a hosting provider, and nothing here needs it yet. SQLite is a single file, costs nothing and is built into Node. All database code is in one file behind a small set of functions, so switching at deploy time means rewriting that file only.
Why does the server run on the PC when nothing should?
It should not, in the end. Hosting it is step 8. For now it is started only for a few seconds to run the live check. One consequence shaped the design: a sandbox in the cloud cannot call back to a server on a PC, so the agent will report its progress by writing to its output, which the orchestrator reads, and not by calling our API.
Why a pass per run, when the gateway already has a key?
The key can do anything, for ever. A sandbox runs commands chosen by an AI model, so it should hold as little as possible: a pass that works for one run, for fifteen minutes, as one role.
Still open
Runs started at the same moment overlap; the one-at-a-time rule is not enforced yet. Sandbox cost is stored on the run but not in the gateway's ledger, though the budget hard stop does see it through Modal's meter.

Step 4 Harness (the agent) Done

Architecture at this step

The harness is the program that turns a model into an agent: it runs the model in a loop and carries out what the model asks for. It lives in agent/, is copied into each run's sandbox, and runs there. It reaches the model only through the gateway, using the run's pass, and reports back by printing one line per event, which the orchestrator reads and stores as it arrives.

Built in earlier steps Added in this step

What this step adds

PieceWhat it is for
The loopAsks the model for one tool call, carries it out, shows the model the result, and repeats. It stops when the model calls "finish", after 8 steps, when the same call is made three times running (stuck), after three unreadable replies, or when the gateway says the budget is spent.
Five toolsRead a file, write a file, search files, run a shell command, and finish. File tools cannot reach outside the repository. Results are cut to 1,500 characters so they fit the model's small window.
The protocolThe instructions that tell the model which tools exist and how to reply, plus a tolerant reader for the replies. Built the way the research recommended: our own instructions, with the reply's shape forced.
Context keeperCounts how much text is being sent and drops the oldest steps before the model's 4,096-token limit is reached, always keeping the instructions and the task. The research showed the model would otherwise lose them silently.
Live eventsThe orchestrator now reads the agent's output line by line as it happens, so the dashboard will be able to show a run in progress.
Kill during workA kill request no longer waits for the current stage: the orchestrator notices within a second, saves the patch so far and destroys the sandbox.

What was checked on the live system

  • Three real tasks ran from "start a run" to a stored patch, in 15 to 26 seconds each.
  • All 9 model replies were valid tool calls. No repairs were needed.
  • One task was completed correctly. One got stuck repeating itself and was stopped by the loop. One was marked done although the result was wrong.
  • A run killed 6 seconds in ended as "killed" within a second, with its sandbox destroyed.
  • Each model call was recorded in the gateway's ledger against its run, as the worker role, using the run's pass.

The results are written up as finding 6 on the Research tab.

Questions this version raises

Where is the "intelligence": in the harness or the model?
In the model. The harness has no opinions about code. It is plumbing with safety rails: it passes messages, runs tools, keeps count, and decides when to stop. Swap in a stronger model and the same harness produces better work.
A run said "done" but the result was wrong. Is that a bug?
Not in the harness: it reported faithfully that the agent called "finish". The gap is that nobody checks the agent's claim. That is the supervisor's review, step 7. Until then, "done" means "the agent says it is done".
Why did a simple "add a line to a file" fail?
The only way to change a file is to write the whole file, and the model wrote just the new line without reading the old content first. A tool for appending or replacing part of a file would avoid that. It has not been added yet; the measurement came first.
Why copy the agent into the sandbox on every run?
It is five small files and takes a moment. The alternative, baking it into the sandbox image, would mean rebuilding the image every time the agent's code changes.
Still open
Whether to add an edit tool now or wait for a larger model. How often this model succeeds on a wider set of tasks; three is too few to say.

How one step of the agent flows

AGENT (in the sandbox)
   │ trims the conversation to fit 4,096 tokens
   │ sends it with the run's pass ───────────────► GATEWAY ──► MODEL
   │                                                  │ budget check, ledger line
   │ ◄── {"tool": "write_file", "args": {...}} ◄──────┘
   │ reads the reply; if unreadable, tells the model and tries again
   │ carries out the tool on the repository
   │ prints an event line ──► ORCHESTRATOR ──► DATABASE (event log)
   └ adds the result to the conversation and goes round again
