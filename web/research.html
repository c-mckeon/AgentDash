Research notes

Small experiments run against the system as it stood on each date, to learn what our choices are good at and where they limit us. One section per date, newest first.

12 October 2026 First measurements: cost tracking, tool calls, context size, first agent runs 6 findings

In short

  • Our cost ledger was recording about an eighth of the real bill. Two causes were found and fixed. After the fixes it matched Modal's bill for the model machine to within 2% on the next batch of calls.
  • Limiting the model to 4 processor threads gave the same writing speed at about half the cost. Left alone, it was using about 19 processor cores, and Modal charges for that.
  • Asking for JSON output fixes the model's tool-call formatting completely. What remains is judgement: it chose the wrong tool in 2 of 10 simple requests, however the question was asked.
  • The model can only read about 4,000 tokens, and it fails silently beyond that. A longer prompt has its beginning cut off with no error, and the beginning is where the task and instructions sit.
  • Waiting costs more than working. One short question costs about 0.7 cents, of which roughly 97% is the machine starting, idling and stopping.

How this was done

Every model call went through the deployed gateway to qwen2.5-coder:1.5b on Modal, with the randomness setting at zero so results repeat. Costs were read from Modal's own billing report before and after each experiment. Sample sizes are small (3 to 10 cases each), so treat the percentages as a first indication. The whole session cost about 6 cents of Modal credit. The script is research/experiments.py and the raw results are in research/results/2026-10-12.jsonl.

1. Our ledger against Modal's bill

The gateway keeps a ledger: one line per model call with an estimated cost. Before this session it said $0.0026 had been spent. Modal's bill said $0.0201. The budget hard stop was reading the ledger, so it would have let spending run to about eight times the limit.

To find the gap, the model machine was woken three times under controlled conditions, with the bill read before and after each:

WakeTime in callsTime billedCores billed (avg)Modal's charge
One tiny call8 s114 s4.0$0.0070
Two long replies, model left alone35 s112 s7.7$0.0123
Two long replies, limited to 4 threads31 s112 s4.0$0.0069

"Time billed" is worked out from Modal's memory charge, which is a flat rate per second the machine exists. "Cores billed" is the processor charge divided by that time.

Cause one: the machine bills for much more than the calls

Each wake was billed for 77 to 106 seconds beyond the calls themselves. We had set the machine to stay up 60 seconds after its last call, and starting and stopping added another 16 to 46 seconds. The ledger had only been counting the calls.

Cause two: the model was using far more processor than we reserved

We reserved 4 cores and priced calls at 4 cores. But Ollama uses every core it can see, and Modal charges for processor actually used above the reservation. While writing, the model was using about 19 cores. Limiting it to 4 threads changed nothing about writing speed (26 tokens per second limited, 23.5 unlimited, same 292-token reply) and cut that wake's cost by 44%.

What was changed

  • The model is now limited to 4 threads, so a second of model time costs what the registry says it costs.
  • The ledger now charges each call for the idle and start/stop time around it.
  • The hard stop now reads Modal's own meter and uses whichever is larger, that or the ledger. Modal's figure is the truth but arrives one to two minutes late; the ledger is instant but an estimate.

On the next batch of 48 calls the ledger recorded $0.0183 against Modal's $0.0186 for the model machine.

Still not in the ledger: the gateway's own small machine (about 6% of the bill so far) and sandboxes. Modal's meter covers both, so the hard stop does too. Because that meter lags, spending can overshoot the limit by whatever is spent in one to two minutes: under a cent at current rates.

2. Getting a tool call out of the model

An agent works by asking for tools: "read this file", "run this command". The smoke test showed this model formats such requests badly. Ten simple requests were tried four ways, each with four tools available (read a file, write a file, search files, run a shell command).

How the model was askedReply usable as it cameRight tool and detailsAvg seconds
Ollama's built-in tool feature0 / 105 / 101.55
Our own instructions: "reply with one JSON object"0 / 108 / 101.39
Our instructions, plus Ollama forced to output JSON10 / 108 / 100.85
Our instructions, plus output forced to match an exact shape10 / 108 / 101.01
  • The built-in tool feature does not work with this model. It never used the proper channel. It wrote the call as text, more than half the time inside a code block, and twice invented tools that do not exist (one named export, one named package.json). It also needed more than twice as many prompt tokens, because the tool definitions are long.
  • Our own instructions got the right answer more often, but every reply was wrapped in a code block or surrounded by explanation.
  • Forcing JSON output removed the formatting problem entirely, and was the fastest. Forcing an exact shape did no better here.
  • The two failures were the same two requests in every approach: "what does src/config.ts export?" (it searched for the word "export" instead of reading the file) and "list the files in the current directory" (it searched instead of running a command). That is weak judgement, which no formatting trick fixes.

For the harness (step 4): describe tools in our own prompt, force JSON output through the gateway, and keep a tolerant parser as a backstop. The gateway gained a response_format option for this.

3. How much the model can read

A fact was placed at the very start of a prompt ("the project codename is BLUEHERON"), followed by increasing amounts of filler code, followed by a question about the fact.

Prompt size (characters)Tokens the model reported readingSecondsRecalled the fact?
1,6025264.6Yes
7,6822,52620.2Yes
15,5822,05019.3No (answered "project127")
23,4822,05019.5No
39,2822,05019.6No
  • The window is 4,096 tokens, roughly 12,000 characters of code. That is small for an agent: a few files and the conversation so far will fill it.
  • Overflow is silent. There is no error. The prompt is cut down to about 2,050 tokens by dropping the beginning, and the model answers confidently from what is left. In an agent, the beginning holds the task and the tool instructions.
  • Reading is slow with 4 threads: about 125 tokens per second, so a full window takes around half a minute per step.

For the harness: it must count tokens itself and keep every request under the limit, because nothing downstream will warn it. The window can be made larger in Ollama's settings at a cost in memory and time; that was not tested.

The smoke test reported reading speeds of 330 to 430 tokens per second. Those were tiny prompts on about 19 cores, so the two figures are not a like-for-like comparison.

6. First real agent runs (added later the same day)

Once the agent existed (step 4), three small tasks were run through the whole system on a tiny public repository, with the agent built the way findings 2 and 3 recommended. Three tasks is a very small sample.

TaskWhat the agent didSystem's verdictActually correct?
Create a file with a given sentence Wrote the file, then finished. 2 model calls. Done Yes
Add a line to the end of an existing file Overwrote the file with only the new line, without reading it first, then repeated the same write twice more. Failed: stopped as "stuck" after the third identical call No, the original content was lost
Write a script that prints 1 to 3, then run it to check Wrote a script that only works in a different shell, ran it, saw the wrong output ({1..3}), searched the file, then declared success. Done No, and the agent's summary said it worked
  • The format problem is solved. All 9 model replies were valid tool calls, with no repairs needed. Forcing the reply's shape, as finding 2 suggested, held up in real use.
  • The stuck detector worked. It caught the repeated write and ended the run after 15 seconds instead of letting it use all its steps.
  • "Done" does not mean "correct". In the third task the agent saw evidence it had failed and reported success anyway. Nothing in the system checks the result yet. This is the job planned for the supervisor's review in step 7, and this run is a concrete example of why it is needed.
  • The model edits by replacing whole files and did not read first, despite being told to. A tool that appends or replaces part of a file, so the model never has to reproduce the rest, would remove this particular failure.
  • Cost: the three runs took 15 to 26 seconds each. Together they cost about 0.8 cents of model time by our ledger and 0.3 cents of sandbox time. The first run carried most of the model cost because it woke the machine.

What this says about our choices

ChoiceWhat is workingWhere it limits us
Modal for everything Machines really do start in seconds and cost nothing when off. Its bill can be read by our own code within a couple of minutes, which is what made this research possible. Billing has rules we did not know: processor use above the reservation is charged, and so is idle and start/stop time. Our own estimates will always be estimates.
A gateway in front of the model Both cost fixes were made in one place and apply to every future caller. The hard stop now rests on the vendor's meter. The meter's delay means the stop can overshoot by a minute or two of spending.
A small model on CPU Fast enough, and cheap per second. Four cores are sufficient. Wrong tool in 2 of 10 trivial requests. If that rate held across the steps of a task, a five-step task would succeed about a third of the time; that is arithmetic from a small sample, and real tasks may be better or worse. The 4,096-token window is tight.
Writing our own harness The approach that worked best (our own tool instructions plus forced JSON) is only available because we control the loop. Ollama's built-in route scored worst. We own every edge case: token counting, truncation, reply repair.
Scaling to zero after 60 idle seconds Nothing is billed while nobody uses the system. Occasional single calls are the most expensive way to use it. Triage and supervisor calls should land while the machine is already awake for a run.

Questions for later

  • Does a larger context window (set in Ollama) work acceptably on 4 cores and 4 GiB?
  • How much does a slightly larger model improve tool choice, and at what cost per run? This is the routing question for step 6.
  • Is 60 seconds the right idle window? Shorter saves money on single calls but risks a wake-up in the middle of a run.
  • Does Ollama's reuse of an already-read prompt make later steps of a run much faster than the 125 tokens per second measured here?
  • How closely does a sandbox's estimated cost match its bill? Three short test sandboxes were billed about $0.0011 in total, in line with the estimate, but that is too little data to say.
