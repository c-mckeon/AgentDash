=== agent/main.ts
--- detail
GOAL
The entry point of the agent. The orchestrator starts it inside
the sandbox with "node /agent/main.ts". It connects the loop in
loop.ts, which is pure logic, to three real things: the gateway
(over HTTP), the repository (through tools.ts), and standard
output (which the orchestrator reads line by line).

THE PARTS WE NEED
1. Five settings read from environment variables.
2. chat(messages): the only function defined in this file. It
   performs one HTTP request to the gateway and converts whatever
   happens into a ChatResult.
3. One call to runAgent(TASK, deps), where deps bundles chat,
   runTool, emit and maxSteps.

WHERE THE DATA COMES FROM AND GOES
- The environment variables are set by executeRun in
  orchestrator/run.ts when it starts this process.
- The messages given to chat are built by runAgent in loop.ts.
- Every event passed to emit is printed with console.log as one
  line of JSON. run.ts reads those lines (its onStdoutLine
  handler) and stores each as an "agent_<type>" event.

@ 6-10 | Imports
Names taken from the other agent files:
- MAX_REPLY_TOKENS (context.ts): the constant 400.
- runAgent (loop.ts): the loop function.
- ChatResult (loop.ts): the type chat must return. "import type"
  means it is used only for checking and vanishes at run time.
- REPLY_SCHEMA (protocol.ts): the JSON schema for a reply.
- runTool (tools.ts): performs one tool call.

@ 12-16 | Read and check the settings
process.env is the table of environment variables for this
process. One line pulls five names out of it:
  GATEWAY_URL, RUN_PASS, TASK, REPO_DIR, MAX_STEPS

If any of the first four is missing or empty:
1. Print a "finished" event with step 0, reason "model_error"
   and the summary "agent started without its settings". It is
   printed in the same JSON form as every other event, so the
   orchestrator records it instead of seeing a silent death.
2. Call process.exit(2). The process ends immediately with exit
   code 2; nothing below this line runs.

MAX_STEPS is not checked here. It gets a default further down.

@ 18-18 | chat(messages): the function's contract
CALLED BY: runAgent, once per turn, as deps.chat.
TAKES:     messages, the conversation already trimmed by
           fitMessages. Each entry has a role and a content.
RETURNS:   a ChatResult, one of
           - ok true, content (the model's reply text), usage
             (the gateway's timing, token and cost figures)
           - ok false, status (a number), error (a message)
The function is async: it returns a promise, and runAgent waits
on it with "await".
It never throws. Every failure path below returns an ok-false
result, so the decision about what a failure means stays in
the loop.

@ 19-25 | chat: send the request
Everything is wrapped in try, so a thrown error lands in the
catch block further down.

1. Call fetch, Node's built-in HTTP client, on
   GATEWAY_URL + "/v1/chat" with:
   - method POST
   - header authorization: "Bearer " + RUN_PASS. The gateway
     verifies this pass and from it knows which run is calling.
   - header content-type: application/json
   - body: one object converted to text by JSON.stringify,
     holding
       messages
       response_format: REPLY_SCHEMA (the gateway forwards it to
         Ollama as "format", which restricts what the model can
         generate)
       max_tokens: MAX_REPLY_TOKENS
       temperature: 0 (always pick the most likely token, so
         runs are repeatable)
   - signal: AbortSignal.timeout(180000), which cancels the
     request and makes fetch throw after 180 seconds.
2. await pauses here until the response headers arrive.

@ 26-28 | chat: turn the response into a ChatResult
3. response.json() reads the body and parses it as JSON. This
   also throws if the body is not JSON.
4. response.ok is false for any status outside 200-299. In that
   case return ok false with response.status and body.error
   (or the status number as text if there is no error field).
   The loop looks for status 402 specifically: the gateway sends
   it when the month's budget is spent.
5. Otherwise return ok true with body.message.content and
   body.usage. The "?." and "??" operators supply "" and {} when
   a field is absent, so a thin response cannot crash the loop.

@ 29-32 | chat: failures that threw
6. catch receives anything thrown above: connection refused,
   DNS failure, the 180-second abort, or unparseable JSON.
   Return ok false with status 0 and the error's message.
   Status 0 is our own marker for "no HTTP status at all".

@ 34-39 | Start the loop
Call runAgent(TASK, deps) and await it. deps is an object
literal built on the spot with four properties:
- chat: the function above.
- runTool: a one-line function (call) => runTool(call, REPO_DIR).
  It fixes the second argument, so the loop only ever passes the
  call and cannot choose a different folder.
- emit: (event) => console.log(JSON.stringify(event)). One event
  becomes one line on standard output.
- maxSteps: Number(MAX_STEPS ?? 8). Environment variables are
  always text, so it is converted; 8 is used if it was not set.

The Outcome that runAgent returns is not used. By then the loop
has already emitted its "finished" event, and the process ends
on its own with exit code 0.

=== agent/loop.ts
--- detail
GOAL
Carry a task to an end by repeatedly asking a model for one tool
call, executing it, and appending the result to the conversation.
The loop must always terminate with a stated reason, including
when the model never calls finish.

THE PARTS WE NEED
1. Five types (ChatResult, StopReason, AgentEvent, LoopDeps,
   Outcome). Types only describe the form of data. They are
   checked while writing the code and removed when it runs.
2. Two constants: REPEAT_LIMIT and PARSE_ERROR_LIMIT.
3. runAgent(task, deps): the exported function.
4. stop(step, reason, summary): a function defined inside
   runAgent, which every exit goes through.

WHERE THE DATA COMES FROM AND GOES
- task is the TASK environment variable, passed in by main.ts.
- deps is built by main.ts (real parts) or by the tests (a
  scripted fake model and a recorder for events).
- Each turn: messages -> fitMessages -> deps.chat -> reply text
  -> parseReply -> ToolCall -> deps.runTool -> ToolResult ->
  appended to messages for the next turn.
- Events go out through deps.emit. The Outcome goes back to
  whoever called runAgent.

STATE KEPT DURING A RUN
- messages: an array that grows by two entries per normal turn
  (the model's reply, then the tool result).
- lastCall, repeats, parseErrors: three counters for the
  stopping rules.

A DESIGN CHOICE
runAgent imports nothing that does I/O. Everything with a side
effect arrives through deps. That is what lets tests/agent.test.ts
run the whole loop in milliseconds with no model.

@ 6-11 | Imports
- fitMessages, and the Message type, from context.ts
- parseReply and systemPrompt, and the ToolCall type, from
  protocol.ts
- clip, and the ToolResult type, from tools.ts

@ 13-15 | type ChatResult
A union of two object forms, told apart by the ok field:
- { ok: true, content, usage }
- { ok: false, status, error }
After code checks "if (!reply.ok)", TypeScript knows which form
it has, and only allows the fields that form really contains.
Produced by chat in main.ts; consumed in runAgent.

@ 17-17 | type StopReason
One of exactly six strings:
- "finished": the model called the finish tool
- "max_steps": the turn limit was reached
- "stuck": the identical call was made three times running
- "parse_errors": three consecutive replies were unreadable
- "budget_exhausted": the gateway answered 402
- "model_error": the request failed for any other reason
run.ts reads this from the final event and maps it to the run's
status (done, failed or budget_stopped).

@ 19-23 | type AgentEvent
An object with
- type: "model", "tool_call", "tool_result", "parse_error" or
  "finished"
- step: the turn number
- any further properties (that is what the "[key: string]:
  unknown" line permits), which differ per type
These become the rows of the dashboard's event feed.

@ 25-30 | type LoopDeps
The dependencies runAgent requires from its caller:
- chat(messages): returns a promise of a ChatResult
- runTool(call): returns a promise of a ToolResult
- emit(event): returns nothing
- maxSteps: a number

@ 32-36 | type Outcome
What runAgent resolves to:
- reason: a StopReason
- steps: the turn it stopped on
- summary: optional text (the "?" marks it optional). Either
  the model's finish summary or an error message.

@ 38-41 | Constants
REPEAT_LIMIT = 3 and PARSE_ERROR_LIMIT = 3.
Both count consecutive occurrences, not totals for the run.

@ 43-50 | runAgent(task, deps): initial state
CALLED BY: main.ts (and the tests).
TAKES:     task, the instruction text; deps, a LoopDeps object.
RETURNS:   a promise of an Outcome.

1. Create the messages array with two entries:
   - role "system", content systemPrompt(): the instructions
     and tool list, generated from the TOOLS table
   - role "user", content "Task: " + task
   fitMessages treats exactly these first two as untouchable.
2. Declare three variables with "let", because they change:
   - lastCall = "": the previous tool call serialised as text
   - repeats = 0: how many times in a row it has occurred
   - parseErrors = 0: consecutive unreadable replies

@ 52-55 | stop(step, reason, summary)
A function defined inside runAgent, so it can use deps directly.
1. Call deps.emit with a "finished" event carrying step and
   reason. summary is included only when one was given: the
   "...(summary ? { summary } : {})" expression adds the property
   or adds nothing.
2. Return the Outcome object { reason, steps: step, summary }.

Every exit is written "return stop(...)", so emitting the final
event and returning the outcome cannot get out of sync.

@ 57-61 | Turn, part 1: call the model
A for loop runs step from 1 to deps.maxSteps inclusive.

3. fitMessages(messages) builds a trimmed copy that fits the
   context window. The full messages array is left intact, so
   nothing is lost from our own record.
4. await deps.chat(...) sends that copy and waits for the
   ChatResult.
5. If reply.ok is false, return stop with reason
   "budget_exhausted" when reply.status is 402, otherwise
   "model_error", and reply.error as the summary.

@ 62-63 | Turn, part 2: record the reply
6. Emit a "model" event containing the reply shortened by
   clip(reply.content, 600) plus the usage figures. Clipping
   keeps stored events small; it affects only the event.
7. Push { role: "assistant", content: reply.content } onto
   messages, unclipped. On the next turn the model is shown its
   own previous output exactly.

@ 65-75 | Turn, part 3: parse the reply
8. parseReply(reply.content) returns either { call } or
   { error }. The test '"error" in parsed' tells them apart.
9. If it is an error:
   a. Emit a "parse_error" event with the message.
   b. "++parseErrors" adds 1 first and then compares. If the
      count has reached PARSE_ERROR_LIMIT, return stop with
      "parse_errors".
   c. Push a user message quoting the error and showing a valid
      example, so the model can correct itself next turn.
   d. "continue" jumps to the next iteration. No tool runs this
      turn, but the turn still counts against maxSteps.
10. Otherwise reset parseErrors to 0.

@ 77-79 | Turn, part 4: handle finish
11. Take call out of parsed.
12. Emit a "tool_call" event with call.tool and call.args.
13. If call.tool is "finish", return stop with "finished" and
    call.args.summary.
    finish is intercepted here and never reaches runTool. It
    exists in the TOOLS table only so the model can select it.

@ 81-84 | Turn, part 5: detect repetition
14. signature = JSON.stringify(call): the tool name and all
    arguments as one string, so equality is a simple comparison.
15. If signature equals lastCall, repeats becomes repeats + 1;
    otherwise repeats becomes 1.
16. Store signature in lastCall.
17. If repeats has reached REPEAT_LIMIT, return stop with
    "stuck" and a summary naming the tool.
    The tool is not run a third time.

@ 86-88 | Turn, part 6: run the tool, feed back the result
18. await deps.runTool(call) performs the tool and returns a
    ToolResult { ok, output }.
19. Emit a "tool_result" event with ok and the output clipped
    to 600 characters.
20. Push { role: "user", content: "Tool result:\n" + output }
    onto messages. The role is "user" because the chat format
    has no separate speaker for tool output; to the model, a
    result is simply the next thing said to it.
The loop then starts the next turn at part 1.

@ 90-90 | After the loop
21. Reaching this line means maxSteps turns passed without a
    finish call. Return stop(deps.maxSteps, "max_steps").

=== agent/protocol.ts
--- detail
GOAL
Define the wire format between the agent and the model: the set
of tools, the instructions that describe them, the schema that
constrains replies, and the parser that reads replies.

Research on 2026-10-12 showed this model does not use Ollama's
native tool-calling channel (0 of 10 calls came back structured),
and that even with forced JSON it sometimes varies the field
names. So tools are described in the prompt, the reply is
constrained by a schema, and the parser repairs the specific
variations that were observed.

THE PARTS WE NEED
1. TOOLS: an object mapping each tool name to a ToolSpec.
2. REPLY_SCHEMA: a JSON schema generated partly from TOOLS.
3. systemPrompt(): builds the instruction text from TOOLS.
4. parseReply(text): converts reply text into a ToolCall or an
   error.
5. Three helpers used only by parseReply: firstJsonObject,
   isObject, plainValue. They are not exported, so no other file
   can call them.

WHERE THE DATA COMES FROM AND GOES
- systemPrompt() is called once by runAgent; its text becomes
  the first message of every request.
- REPLY_SCHEMA is sent by chat in main.ts with every request.
- parseReply receives reply.content from runAgent each turn and
  returns a ToolCall, which runAgent passes to runTool.

A DESIGN CHOICE
TOOLS is the single source of truth. The prompt, the schema's
list of allowed names, and the parser's argument check are all
computed from it. Adding a tool means one entry here plus its
behaviour in tools.ts.

@ 10-13 | interface ToolSpec
The form of one entry in TOOLS:
- description: a sentence shown to the model
- args: an object mapping each argument name to a short note.
  The parser uses the names; the notes are documentation.

@ 15-35 | const TOOLS
An object with seven entries. Key = tool name, value = ToolSpec.
- read_file: path
- write_file: path, content (replaces the whole file)
- append_file: path, content (added at the end)
- replace_in_file: path, find, replace (first exact match)
- search_files: pattern
- run_shell: command
- finish: summary

All arguments are strings. That keeps the reply format flat
enough for a 1.5-billion-parameter model to produce reliably.

append_file and replace_in_file were added after the first
recorded runs: asked to add a line to README, the model called
write_file with only the new line and erased the rest.

@ 37-40 | interface ToolCall
The parsed form of a reply:
- tool: a key of TOOLS
- args: an object of argument name to string value
Created only by parseReply, so anything holding a ToolCall can
assume it has already been validated.

@ 42-47 | const REPLY_SCHEMA
A JSON schema object stating that a reply is
- an object
- with property "tool": a string whose value must be one of
  Object.keys(TOOLS), i.e. the seven names, computed here
- with property "args": an object
- both required
Ollama applies this while generating: at each token, choices
that would violate the schema are removed. The schema does not
say which arguments each tool needs, so parseReply checks that.

@ 49-60 | systemPrompt()
CALLED BY: runAgent, once, when it creates the conversation.
TAKES:     nothing.
RETURNS:   the instruction text.

1. Object.entries(TOOLS) gives [name, spec] pairs. map turns
   each into the line "- name(arg1, arg2): description", and
   join("\n") puts them on separate lines.
2. Build an array of five strings and join them with newlines:
   a. the role: a coding agent that acts only through tools,
      one call per reply
   b. the working rules: results are shown after each call;
      inspect before changing; call finish when done
   c. "Tools:" and the lines from step 1
   d. the required reply form
   e. one concrete example

The text is rebuilt from TOOLS on each call, so it can never
list a tool that does not exist. It is deliberately short: it
occupies part of the 4,096-token window on every request.

@ 62-64 | firstJsonObject(text): outer loop
CALLED BY: parseReply, only when the whole reply is not JSON.
TAKES:     the reply text.
RETURNS:   the first substring that parses as JSON, already
           parsed; or null.

Handles replies such as: Sure! {"tool": ...} Let me know.

1. text.indexOf("{") finds the first opening brace. The for
   loop repeats from each later "{" until indexOf returns -1,
   meaning there are no more.

@ 65-76 | firstJsonObject: find the matching closing brace
For the current "{" at position start:
2. Set depth = 0, inString = false, escaped = false.
3. Read one character at a time from start:
   - While inString is true: a character after a backslash is
     skipped (escaped); a backslash sets escaped; an unescaped
     double quote ends the string.
   - Otherwise: a double quote sets inString; "{" increments
     depth; "}" decrements depth.
   - When a "}" brings depth back to 0, this is the brace that
     closes the one we started from.
The string tracking is essential: file content passed as an
argument routinely contains braces, and those must not be
counted.

@ 77-86 | firstJsonObject: try to parse the candidate
4. text.slice(start, index + 1) is the candidate. JSON.parse
   either returns the parsed value, which we return at once, or
   throws.
5. If it throws, the empty catch swallows the error and "break"
   leaves the inner loop, so the outer loop moves on to the next
   "{" in the text.
6. If the outer loop finishes without returning, return null.

@ 88-89 | isObject(value)
Returns true only when value is a plain object: typeof is
"object", it is not null, and it is not an array. All three
tests are needed because in JavaScript typeof null and typeof
an array are both "object".
The "value is Record<...>" return type tells TypeScript that
after this check the value's properties may be read.

@ 91-94 | plainValue(value)
Repairs one observed mistake: instead of "README.md" the model
sometimes echoes schema syntax and writes
{"type": "string", "value": "README.md"}.
If value is an object containing a "value" property, return
that property; otherwise return value unchanged.

@ 96-103 | parseReply(text): obtain an object
CALLED BY: runAgent, every turn, with reply.content.
TAKES:     the raw reply text from the model.
RETURNS:   { call: ToolCall } or { error: string }. It never
           throws; runAgent sends the error text back to the
           model.
RULE:      repair only shapes that were actually observed, and
           reject everything else rather than guess.

1. Try JSON.parse(text.trim()). With the schema enforced this
   normally succeeds.
2. If it throws, fall back to firstJsonObject(text).
3. If the result is not a plain object, return the error
   "the reply contained no JSON object".

@ 105-108 | parseReply: identify the tool
4. tool = found.tool ?? found.name. "??" means: use the right
   side only if the left is missing. "name" is accepted because
   it is the spelling used by standard tool-calling formats,
   which the model sometimes falls back to.
5. If tool is not a string, or is not a key of TOOLS, return an
   error that lists the valid names. Sent back to the model,
   that error doubles as a reminder of the tool list.

@ 110-112 | parseReply: locate the arguments
6. Take the first of found.args, found.arguments and
   found.parameters that is a plain object.
7. If one exists and is non-empty, use it as source. Otherwise
   use found itself, which covers a flat reply such as
   {"tool": "read_file", "path": "README.md"}.

@ 113-119 | parseReply: extract exactly the declared arguments
8. Create an empty args object.
9. Loop over Object.keys(TOOLS[tool].args), the names this tool
   declares:
   a. value = plainValue(source[name])
   b. number or boolean: store String(value)
   c. string: store it unchanged
   d. anything else (missing, null, object, array): return an
      error naming the tool and the argument
Only declared names are copied, so any extra properties the
model invented are dropped here.

@ 120-120 | parseReply: result
10. Return { call: { tool, args } }.

=== agent/context.ts
--- detail
GOAL
Guarantee that a request never exceeds the model's context
window.

The window is 4,096 tokens (num_ctx in Ollama), covering the
prompt and the reply together. Research on 2026-10-12 showed
that Ollama handles an over-long prompt by silently discarding
tokens from its START. The start holds the system prompt and
the task, so the model continues with no idea what it was asked.
No error is returned. The agent therefore measures its own
prompt and removes old steps before sending.

THE PARTS WE NEED
1. The Message type.
2. Three numeric constants and one string constant.
3. estimateTokens(text): a cheap size estimate.
4. total(messages): the estimate for a whole conversation.
5. fitMessages(messages, budget): returns the list to send.

WHERE THE DATA COMES FROM AND GOES
- runAgent calls fitMessages(messages) each turn and passes the
  result straight to deps.chat.
- main.ts sends MAX_REPLY_TOKENS as max_tokens, so the model
  cannot produce a reply longer than the space reserved here.

AN ASSUMPTION THIS FILE RELIES ON
messages has the layout runAgent builds: index 0 is the system
prompt, index 1 is the task, and everything from index 2 on is
alternating (assistant reply, user result) pairs.

@ 9-12 | interface Message
- role: "system", "user" or "assistant"
- content: the text
This is the message form of the chat API that the gateway
forwards to Ollama unchanged.

@ 14-17 | The budget constants
- CONTEXT_WINDOW_TOKENS = 4096
- MAX_REPLY_TOKENS = 400
- PROMPT_BUDGET_TOKENS = 4096 - 400 - 300 = 3396
The 300 is a margin for estimation error, since we do not run
the model's real tokenizer.

@ 19-19 | const OMITTED_NOTE
The string "[Earlier steps were removed to save space.]".
Inserted where steps were dropped, so the model is told its
history is partial instead of seeing an unexplained jump.
Exported because the tests look for it.

@ 21-24 | estimateTokens(text)
CALLED BY: total, and the tests.
TAKES:     any string.
RETURNS:   Math.ceil(text.length / 3), an integer.

The real ratio measured on code was about 3.04 characters per
token. Dividing by 3 overestimates slightly, which errs towards
trimming too early rather than overflowing.

@ 26-27 | total(messages)
Not exported; used only by fitMessages.
TAKES:     an array of messages.
RETURNS:   reduce over the array, summing
           estimateTokens(message.content) + 4 for each.
The + 4 approximates the role marker and delimiters the chat
template wraps around every message.

@ 34-39 | fitMessages(messages, budget): setup
CALLED BY: runAgent, before each request.
TAKES:     messages, the full conversation; budget, which
           defaults to PROMPT_BUDGET_TOKENS (tests pass smaller
           values).
RETURNS:   a new array, safe to send.

1. fixed = messages.slice(0, 2): the system prompt and the task.
2. steps = messages.slice(2): a new array of the rest. slice
   copies the array, so removing items from steps does not
   touch the caller's messages.
3. dropped = false.
4. assemble() is a small inner function that builds the
   candidate result: fixed + steps, with a user message holding
   OMITTED_NOTE inserted between them once dropped is true.

@ 41-44 | fitMessages: drop the oldest pairs
5. while total(assemble()) > budget and steps.length > 2:
   a. steps.splice(0, 2) removes the two oldest entries in
      place: one assistant reply and its tool result. Removing
      pairs keeps the roles alternating correctly.
   b. Set dropped = true.
The "length > 2" condition keeps the most recent pair no matter
what: the model must see the result of its last action.

@ 45-52 | fitMessages: shorten one oversized step
The loop above can end while still over budget, when a single
remaining step is very large (a big file was read).

6. fitted = assemble().
7. while total(fitted) > budget:
   a. reduce over fitted.slice(2) to find the message with the
      longest content. The fixed two are excluded.
   b. If none exists or it is under 200 characters, break.
      Nothing useful is left to cut.
   c. Replace its content with the first half plus
      "\n[cut to fit]", then reassemble and test again.
Step c assigns to the message object itself. That object is
shared with the caller's array, so the shortened text is also
what stays in the stored conversation from then on.

@ 53-53 | fitMessages: result
8. Return fitted.

=== agent/tools.ts
--- detail
GOAL
Execute tool calls inside the sandbox. protocol.ts defines what
the model may ask for; this file is what actually happens.

Two guarantees:
1. The four file tools cannot read or write outside the
   repository directory.
2. runTool never throws. Every failure is returned as a result
   whose output starts with "ERROR:", because the consumer is
   the model, and it can often recover when told what failed.

THE PARTS WE NEED
1. The ToolResult type.
2. Two constants: OUTPUT_LIMIT and SHELL_TIMEOUT_MS.
3. clip(text, limit): truncate with a visible marker.
4. insideRepo(repoDir, path): the path-containment check.
5. run(file, args, cwd): start a child process and collect its
   exit code and output. Not exported.
6. runTool(call, repoDir): dispatch on the tool name.

WHERE THE DATA COMES FROM AND GOES
- call is the ToolCall produced by parseReply, so call.tool is
  a known name and every declared argument is a string.
- repoDir is the REPO_DIR environment variable
  (/workspace/repo), fixed by the wrapper in main.ts.
- The ToolResult returns to runAgent, which emits it as an
  event and appends its output to the conversation.

SIDE EFFECTS
Files created or changed in the repository, and child processes
(rg and sh) started inside the sandbox. The orchestrator later
captures the file changes with "git diff" as the run's patch.

@ 2-6 | Imports
From Node's standard library:
- execFile (node:child_process): start a program directly, with
  its arguments as an array, not through a shell
- mkdir, readFile, writeFile (node:fs/promises): the versions of
  the file functions that return promises
- dirname, resolve, sep (node:path): path arithmetic
And the ToolCall type from protocol.ts.

@ 8-11 | interface ToolResult
- ok: boolean
- output: the text shown to the model. Either the content it
  requested, a one-line confirmation, or "ERROR: ...".

@ 13-15 | Constants
- OUTPUT_LIMIT = 1500 characters, roughly 500 tokens. A result
  stays in the conversation and is re-sent every later turn, so
  its size is paid for repeatedly.
- SHELL_TIMEOUT_MS = 30000 milliseconds.

@ 17-19 | clip(text, limit)
CALLED BY: runTool for its outputs, and runAgent for events
           (with limit 600).
TAKES:     text; limit, defaulting to OUTPUT_LIMIT.
RETURNS:   text unchanged if text.length <= limit; otherwise
           text.slice(0, limit) followed by
           "[cut: N characters in total]".
The total is included so the model can tell that it has seen
only part of the content.

@ 21-26 | insideRepo(repoDir, path)
CALLED BY: runTool, for the four file tools.
TAKES:     repoDir; path, the model's args.path, which may be
           relative, absolute, or contain "../".
RETURNS:   the absolute path if it lies inside the repository,
           otherwise null.

1. root = resolve(repoDir): the repository as an absolute path.
2. target = resolve(root, path): path interpreted relative to
   root, with "." and ".." segments collapsed. An absolute path
   replaces root entirely.
3. Return target if target === root, or if target starts with
   root + sep (sep is "/" on Linux). Otherwise return null.

"../../etc/passwd" resolves to /etc/passwd and fails the test.
Appending sep prevents /workspace/repo-other from passing as a
prefix match of /workspace/repo.

@ 28-35 | run(file, args, cwd)
CALLED BY: runTool, for search_files and run_shell.
TAKES:     file, the program name; args, its arguments as an
           array; cwd, the working directory.
RETURNS:   a promise of { code, stdout, stderr }.

1. Create a new Promise. Its "done" function is what will
   eventually deliver the result.
2. Call execFile with a timeout of SHELL_TIMEOUT_MS and a
   maxBuffer of 1 MB of output. execFile calls our callback
   once, when the program has exited or been killed.
3. In the callback, compute code:
   - no error object: 0
   - error.code is a number: the program's own exit code
   - otherwise (it could not start, or was killed): 1
4. If error.killed is true, the timeout fired; append
   "[stopped after 30 s]" to stderr.
5. Call done with the three values.

done is called on every path and the promise is never rejected,
so callers can await run without a try/catch.

TAKES:     call, a validated ToolCall; repoDir.
RETURNS:   a promise of a ToolResult.

1. Destructure tool and args from call.
2. Open a try block around the whole body. Its catch is the

@ 65-70 | search_files
4. If tool is search_files:
   a. await run("rg", [...], repoDir) with the arguments

      The "--" marks the end of options, so a pattern beginning
