=== api/main.ts
Starts the real API on this machine, wired to a real database file and real Modal sandboxes.

@ 1-11 | Gather the parts
load .env
read the settings
open the database
connect to Modal for sandboxes

@ 13-20 | Start listening
create the API with:
    the database
    the owner's token
    "start a run" = hand it to the orchestrator and do not wait for it
listen on the configured port

=== api/server.ts
The web interface to the system. Anyone may read runs and their events; only the owner may start or kill one.

@ 1-24 | What this file is
Plain Node HTTP, no framework.
Limits:
    repositories must be public GitHub addresses, so a sandbox never needs a password
    a task may be at most 4,000 characters
    a request body may be at most 64 KB
The API needs: the database, the owner's token, and a way to start a run.

@ 26-35 | Check a new run request
to validate a new run:
    it must be an object
    task must be non-empty text, not too long
    repoUrl must look like https://github.com/owner/name
    return the cleaned task and repoUrl, or a sentence saying what is wrong

@ 37-41 | Is this the owner?
compare the token in the request with the owner's token
    (compared in constant time, so timing cannot leak it)

@ 43-57 | Read and write JSON
to read a request body: collect it piece by piece, refusing anything over 64 KB, then parse it
to send a reply: set the status, mark it as JSON, write it

@ 59-69 | Route the request
for every request:
    split the address into: root / run id / action
    GET /health: reply ok
    anything not under /runs: 404

@ 71-89 | /runs: list or start
    with no run id:
        GET: reply with the list of runs
        POST:
            not the owner: 401
            body is not JSON: 400
            fails validation: 400 with the reason
            create the run with a random id, status "queued"
            record a "queued" event
            hand the run to the orchestrator
            reply 201 with the run
        anything else: 405

@ 91-100 | /runs/:id: read a run or its events
    look up the run; 404 if it does not exist
    GET /runs/:id: reply with the run and its model choices
    GET /runs/:id/events?after=N: reply with events newer than N
        (this is how a dashboard would follow a run live)

@ 101-107 | /runs/:id/kill
    POST /runs/:id/kill:
        not the owner: 401
        run already ended: 409
        mark the run "kill requested" and record the event
        reply 202 (accepted; the orchestrator does the actual stopping)

@ 108-113 | Anything else
    unknown action: 404
    if anything throws: 500 with the message

=== db/index.ts
Everything that touches stored data. It uses SQLite, a database that is a single file. The rest of the system calls only these functions, so swapping the database later means rewriting this file alone.

@ 1-11 | What this file is
Uses the SQLite driver built into Node: no account, no cost.
Borrows the lifecycle rules from orchestrator/state.ts.

@ 13-43 | The three tables
runs: one row per run
    id, task, repository, status, kill-requested flag,
    patch, error, sandbox seconds and cost, created and updated times
events: one row per thing that happened in a run, numbered in order
    run id, time, type, data
model_assignments: one row each time a model is chosen for a run
    run id, time, tier, who decided, why

@ 45-73 | The same things as TypeScript shapes
Run, RunEvent and ModelAssignment describe a row from each table in the form the rest of the code uses.

@ 75-97 | Convert database rows
database columns are named like repo_url; the code uses repoUrl
toRun and toEvent do that renaming, and turn stored JSON text back into data

@ 99-111 | Open the database
on creation:
    open the file (or an in-memory database for tests)
    create the tables if they are not there
    keep a clock, so tests can control the time

@ 113-128 | Create and read runs
createRun: insert a row with status "queued", return it
getRun: fetch one run by id, or nothing
listRuns: the newest 50 runs

@ 130-139 | Change a run's status
setStatus:
    fetch the run; fail if it does not exist
    ask the lifecycle rules whether this move is allowed; fail if not
    store the new status, any error, and the time

@ 141-153 | Flags and results
requestKill: set the kill-requested flag
savePatch: store the patch
saveSandboxUsage: store how long the sandbox lived and what it cost

@ 155-169 | Events
appendEvent: add an event to a run, return it with its number
listEvents: a run's events in order; given a number, only the ones after it

@ 171-193 | Model choices, and closing
addAssignment: record which model tier was chosen, by whom and why
listAssignments: a run's model choices in order
close: close the database
